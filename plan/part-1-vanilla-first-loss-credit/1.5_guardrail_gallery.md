# Phase 1.5 — Guardrail Gallery

Part 1 (Vanilla) · Project: first-loss-credit · Spec: merged XLS-65/66.

## Objective
Reproduce each protocol guardrail rejection the hackathon minimum bar requires, each as an
isolated, reproducible case where **all other preconditions pass** so the failing reason is
unambiguous. This phase is the event's "rejected transaction caused by a protocol guardrail"
deliverable, done exhaustively for the report.

## Independence contract
Inputs: none. Outputs consumed downstream: none. Each case below builds its own minimal
substrate. Cases do not share state.

## Cases (each a standalone sub-run)

### A. Insufficient liquidity on VaultWithdraw
- Build: vault funded by the lender, most assets committed to an outstanding loan so
  `AssetsAvailable < requested`.
- Ensure the lender **owns enough shares** for the requested amount (so the failure is
  liquidity, not share balance).
- **VaultWithdraw** (`tt=69`) requesting more than `AssetsAvailable` → **`tecINSUFFICIENT_FUNDS`**.

### B. Insufficient liquidity on LoanSet
- Build: vault with `AssetsAvailable < PrincipalRequested`; broker with enough cover and
  debt capacity so those checks pass.
- **LoanSet** (`tt=80`) with `PrincipalRequested > AssetsAvailable` → **`tecINSUFFICIENT_FUNDS`**.

### C. Cover below minimum blocks a new loan
- Build: broker whose `CoverAvailable < (DebtTotal + PrincipalRequested + InterestDue) *
  CoverRateMinimum`; vault has ample liquidity (so liquidity is not the cause).
- **LoanSet** → **`tecINSUFFICIENT_FUNDS`** (cover check #20). This blocks a *new loan*.

### D. Deposit over the vault cap
- Build: vault created with a finite `AssetsMaximum`; depositor well funded.
- **VaultDeposit** (`tt=68`) that pushes total above `AssetsMaximum` → **`tecLIMIT_EXCEEDED`**.

### E. Late payment without the late flag ("out-of-schedule")
- Build: an overdue loan (`now > NextPaymentDueDate`).
- **LoanPay** (`tt=84`) **without** `tfLoanLatePayment` (`0x00040000`) → **`tecEXPIRED`**.
- Positive control: the same payment **with** `tfLoanLatePayment` and the late total →
  `tesSUCCESS`.

### F. On-time payment below the required amount
- Build: a current loan.
- **LoanPay** with `Amount < PeriodicPayment + LoanServiceFee` → **`tecINSUFFICIENT_PAYMENT`**.
- **Verified nuance:** truncating `PeriodicPayment` by its **sub-drop** fraction (e.g.
  `20000038.19 → 20000038`) is **accepted** (`tesSUCCESS`) on this build — the rejection needs a
  real shortfall (e.g. paying half). So "round down → `tecINSUFFICIENT_PAYMENT`" overstates it;
  rounding **up** is still the safe rule, but a sub-unit truncation alone does not fail here.

### G. Debt cap exceeded
- Build: broker with a low `DebtMaximum`.
- **LoanSet** pushing `DebtTotal` over `DebtMaximum` → **`tecLIMIT_EXCEEDED`**.

### H. Cover withdrawal below the minimum
- Build: broker with outstanding debt (`DebtTotal > 0`) and cover at the minimum.
- **LoanBrokerCoverWithdraw** (`tt=77`) dropping `CoverAvailable` below
  `DebtTotal * CoverRateMinimum` → **`tecINSUFFICIENT_FUNDS`**. Distinct from Case C: Case C
  blocks a new `LoanSet`; Case H blocks a cover **withdraw**.

## Expected results and assertions (✅ all 8 verified live on the hackathon devnet)
For every case: the listed `tec` code, plus a positive control that succeeds once the single
blocking condition is removed. Assert the exact code string from the result metadata. Verified
codes: A/B/C/H `tecINSUFFICIENT_FUNDS`, D/G `tecLIMIT_EXCEEDED`, E `tecEXPIRED`,
F `tecINSUFFICIENT_PAYMENT`. For a LoanSet expected to fail (B/C/G), submit the **already
dual-signed blob** directly — do not re-autofill/re-sign, which would drop the counterparty
signature.

## Explorer verification
Record each failing tx hash and its paired positive control.

## Precision and timing rules
- `tecEXPIRED` specifically means **late without `tfLoanLatePayment`** — label it exactly,
  not "out-of-schedule".
- Case F depends on rounding direction; demonstrate the failure, then the fix.

## Friction to capture
- For each rejection: did the error code point at the actual cause, or was it generic?
- Which guardrail was hardest to trigger cleanly without a second failure masking it?
