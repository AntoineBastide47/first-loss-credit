# Phase 1.2 — Loan Broker and First-Loss Cover

Part 1 (Vanilla) · Project: first-loss-credit · Spec: merged XLS-66.

## Objective
Create a loan broker on a funded vault, deposit first-loss capital (cover), read the cover
parameters, then prove the cover-minimum guardrail by attempting a withdraw that would drop
cover below the required minimum while real debt is outstanding.

## Independence contract
Inputs: none. Outputs consumed downstream: none. This phase builds its own vault, broker,
and one outstanding loan solely to create debt against which the cover minimum is tested.

## Preconditions this phase builds
1. Fund `lender`, `brokerOwner`, `borrower`.
2. Vault (XRP asset) with a lender deposit large enough to fund one loan.
3. A loan broker; cover deposited; one loan originated so `DebtTotal > 0`.

## Actors
| Role | Purpose |
|------|---------|
| brokerOwner | creates the broker, deposits/withdraws first-loss cover |
| lender | funds the vault so a loan can draw |
| borrower | takes one loan so `DebtTotal > 0` for the minimum test |

## Transaction steps (exact fields)
1. **LoanBrokerSet** (`tt=74`), `Account=brokerOwner`.
   - `VaultID` (the funded vault).
   - `ManagementFeeRate` (UINT16, 1/10 bps, range **0-10000**; out of range → `temINVALID`).
     Note the cover rates below use 0-100000, a different range — do not cross-apply.
   - `DebtMaximum` (cap on total debt; set generous).
   - `CoverRateMinimum` (1/10 bps): fraction of `DebtTotal` that must be covered.
   - `CoverRateLiquidation` (1/10 bps): fraction of the minimum cover liquidated per default.
   - Capture `LoanBrokerID` from metadata. Costs 2 owner reserves (object + pseudo-account).
2. **LoanBrokerCoverDeposit** (`tt=76`), `Account=brokerOwner`, `LoanBrokerID`, `Amount`.
   - Read: `LoanBroker.CoverAvailable == Amount`.
3. Originate one loan (see 1.3 for full field set) so `DebtTotal > 0`.
4. **LoanBrokerCoverWithdraw** (`tt=77`), `Account=brokerOwner`, `LoanBrokerID`, `Amount`
   chosen so `CoverAvailable - Amount < DebtTotal * CoverRateMinimum`.

## Expected results and assertions
- Steps 1-3: `tesSUCCESS`. Read `CoverAvailable`, `DebtTotal`, `CoverRateMinimum`,
  `CoverRateLiquidation`, `ManagementFeeRate` from the `LoanBroker` object.
- Step 4: **`tecINSUFFICIENT_FUNDS`** — the withdraw is rejected because it would drop cover
  below `DebtTotal * CoverRateMinimum`. Make all other checks pass (broker owns the object,
  amount ≤ `CoverAvailable`) so the failure is unambiguously the cover minimum.
- Follow-up positive control: a **smaller** withdraw that keeps cover ≥ minimum returns
  `tesSUCCESS`.

## Explorer verification
Record `LoanBrokerSet`, `LoanBrokerCoverDeposit`, the failed and the successful
`LoanBrokerCoverWithdraw` hashes.

## Precision and timing rules
- Cover rates are 1/10 bps integers; convert percentages carefully
  (`1% = 1000`, `100% = 100000`).
- While `CoverAvailable < DebtTotal * CoverRateMinimum`, the broker cannot issue new loans
  and fees route to the cover pool, not the owner. Note this for the report.

## Friction to capture
- Did `CoverRateMinimum` / `CoverRateLiquidation` behave as their names suggest?
- Was the 1/10 bps unit obvious, or did it cause a first wrong value?
- Did the rejection error point at the cover minimum, or was it generic?
