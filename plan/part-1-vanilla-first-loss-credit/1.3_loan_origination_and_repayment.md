# Phase 1.3 — Loan Origination and Repayment

Part 1 (Vanilla) · Project: first-loss-credit · Spec: merged XLS-66.

## Objective
Originate a loan with the dual-signature `LoanSet`, confirm the borrower receives principal
minus origination fee **inside** `LoanSet` (no separate draw), then make one or more
`LoanPay` payments and confirm the accounting: interest is booked at origination, `LoanPay`
returns liquid assets.

## Independence contract
Inputs: none. Outputs consumed downstream: none. This phase builds its own vault (funded),
broker (with cover), borrower, then runs the full loan.

## Preconditions this phase builds
1. Fund `owner` (vault + broker owner), `lender`, `borrower`.
2. Vault (`Asset: { currency: "XRP" }`) with a deposit ≥ the loan principal.
3. Broker with `CoverAvailable ≥ (DebtTotal + PrincipalRequested + InterestDue) *
   CoverRateMinimum` so origination passes the cover check.

## The dual-signature LoanSet (merged spec, single transaction)
- One transaction carries **two** approvals. The initiator signs normally
  (`SigningPubKey`/`TxnSignature` or `Signers`).
- The counterparty approval goes in the inner `STOBJECT` field **`CounterpartySignature`**
  (`SigningPubKey` + `TxnSignature`) **or** a `Signers` list — exactly one form.
- `CounterpartySignature` is **excluded** from the primary signature (not a signing field).
- Fee ≥ `2 * base_fee`; formula `(1 + |Signers| + |counterparty signers|) * base_fee`
  outside a Batch.
- Use xrpl.js `signLoanSetByCounterparty(...)` / `combineLoanSetCounterpartySigners(...)`
  (`Wallet/counterpartySigner.ts`) to build the counterparty field.

## Transaction steps (exact fields)
1. **LoanSet** (`tt=80`), initiator = `owner` (broker) or `borrower`.
   - Required: `LoanBrokerID`, `PrincipalRequested` (an **XRPLNumber string**, e.g. `"1000"`),
     `CounterpartySignature`.
   - `Counterparty`: **when the broker initiates, set it to the borrower (required).** When
     the **borrower** initiates, `Counterparty` **defaults to `LoanBroker.Owner`** and may be
     omitted.
   - Terms (optional): `InterestRate` (annualized, 1/10 bps), `PaymentInterval` (≥60 s,
     default 60), `PaymentTotal` (default 1), `GracePeriod` (≥60 s and ≤ `PaymentInterval`),
     `LoanOriginationFee`, `LoanServiceFee`, `LatePaymentFee`, `ClosePaymentFee`,
     `LateInterestRate` / `CloseInterestRate` / `OverpaymentInterestRate` as needed.
   - Capture `LoanID` (hash of namespace + `LoanBrokerID` + `LoanBroker.LoanSequence`).
2. **LoanPay** (`tt=84`), `Account=borrower`, `LoanID`, `Amount ≥ PeriodicPayment +
   LoanServiceFee`. Repeat for each period.
   - To settle a loan **early**, set `tfLoanFullPayment` (`0x00020000`) while **more than
     one** payment remains (`PaymentRemaining > 1`). Do **not** set it on the final scheduled
     payment (`PaymentRemaining == 1`) — the final payment must be a plain payment, or it
     returns `tecKILLED`.

## Expected results and assertions (✅ verified live on the hackathon devnet)
- **At `LoanSet`:** `Vault.AssetsAvailable -= PrincipalRequested`. **Cash basis
  (`LendingProtocolV1_1`): `Vault.AssetsTotal` is UNCHANGED at origination** (no accrual). Note
  interest via the loan object: `TotalValueOutstanding = PrincipalRequested + interest` while
  `PrincipalOutstanding = PrincipalRequested`. **`LoanBroker.DebtTotal += PrincipalRequested`
  only** (principal, not principal+interest); `LoanBroker.LoanSequence += 1`. Borrower balance
  increases by `PrincipalRequested - LoanOriginationFee` (less its own tx fee); the
  `LoanOriginationFee` is paid to `owner` (verified: owner balance += fee exactly).
- **At `LoanPay`:** the payment returns to the vault pseudo-account, raising `AssetsAvailable`
  (and `AssetsTotal` by the interest recognized then); fees go to the broker (or the cover pool
  if cover is below minimum). `PrincipalOutstanding`, `TotalValueOutstanding`, `PaymentRemaining`
  decrease.
- **Interest is recognized on `LoanPay`, NOT at origination** (opposite of the earlier
  assumption). Assert `AssetsTotal` rises only after payment.
- Negative controls (both verified `tecKILLED`): `tfLoanFullPayment` on the final payment
  (`PaymentRemaining == 1`); and paying an already fully-paid loan (the `Loan` object is **not**
  deleted on full payment — it remains at `PaymentRemaining == 0`, so a further `LoanPay`
  returns `tecKILLED`).
- Positive: `tfLoanFullPayment` while `PaymentRemaining > 1` settles the loan early
  (`tesSUCCESS`); a plain final payment (no flag) at `PaymentRemaining == 1` succeeds.

## Explorer verification
Record `LoanSet` (showing two signatures) and each `LoanPay`; show borrower receipt of
`Principal - OriginationFee` and vault balance changes.

## Precision and timing rules
- `PeriodicPayment`, `TotalValueOutstanding`, `ManagementFeeOutstanding` are high-precision
  decimals. Compute the required `LoanPay` amount and **round up** to the asset unit, or the
  on-time payment can fall short and return `tecINSUFFICIENT_PAYMENT`.
- Rates are annualized in 1/10 bps.
