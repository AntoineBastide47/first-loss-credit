# Phase 6.5 — Guardrail Explainer

Part 6 (UI) · Spec surface: XLS-65/66 result codes · Composes `6.0`.

## Objective
Turn protocol rejections into plain-language explanations. A reusable layer that maps each
`tec*`/`tem*` code to its real cause in this domain, plus a gallery that triggers each guardrail
on demand. This is the UI face of the "rejected transaction caused by a guardrail" deliverable.

## Independence contract
Inputs: none required beyond a connected wallet for the live gallery (which builds its own
substrate via the shared builders). References no other UI phase and no backend phase; depends
on no future phase; reads no other phase's runtime state.

## Two deliverables
1. **Explainer layer** (`ui/result-explainer`): a pure function `explain(txType, code, context)`
   → `{ title, cause, fix }`, consumed by every `TxButton` in Part 6 so any rejection anywhere
   renders a human cause, not a raw code.
2. **Guardrail gallery screen** (`/guardrails`): a card per case that, on click, builds the
   minimal substrate via the shared builders, triggers the rejection live, and shows the code +
   explanation + explorer link, then runs the positive control.

## Code → cause map (verified; the explainer's seed data)
| Context | Code | Plain cause | Fix |
|---|---|---|---|
| VaultWithdraw | `tecINSUFFICIENT_FUNDS` | not enough **liquid** assets (committed to loans) | withdraw ≤ `AssetsAvailable`, or wait for repayment |
| LoanSet | `tecINSUFFICIENT_FUNDS` | vault liquidity **or** cover below minimum | add liquidity / add cover |
| CoverWithdraw | `tecINSUFFICIENT_FUNDS` | would breach the **cover ratio** (funds exist) | withdraw less; keep cover ≥ `DebtTotal*CoverRateMinimum` |
| VaultDeposit | `tecLIMIT_EXCEEDED` | over the vault `AssetsMaximum` cap | deposit less |
| LoanSet | `tecLIMIT_EXCEEDED` | over the broker `DebtMaximum` | smaller principal / raise cap |
| LoanPay | `tecEXPIRED` | late payment without `tfLoanLatePayment` | set the late flag (+ late total) |
| LoanPay | `tecINSUFFICIENT_PAYMENT` | below the period's required amount | pay ≥ `PeriodicPayment`, rounded **up** |
| LoanPay | `tecKILLED` | `tfLoanFullPayment` on the final payment, or paying a settled loan | plain final payment / stop |
| LoanManage | `tecTOO_SOON` | impair before overdue, or default before grace end | wait for the window |

## Build steps
1. `explain()` from the table; wire it into the shared `TxButton` so the whole UI uses it.
2. `/guardrails` screen: one card per row; each builds its substrate with the shared builders,
   fires the failing tx (via the no-throw submit helpers), shows code + `explain()` + link, then
   the positive control.
3. A "copy report" action that lists each case's failing hash and control hash.

## Acceptance checks
- Every row triggers its listed code live and renders the correct explanation.
- Each case pairs with a succeeding positive control.
- A rejection from any other Part 6 screen renders the same human explanation (shared layer).

## Verification
Explorer links for each failing tx and its control; codes match the table.

## Precision / UX rules
- Show the raw code and the explanation together (never hide the code).
- `tecINSUFFICIENT_FUNDS` is context-dependent — the explainer must use `txType`/`context` to
  pick the right cause (liquidity vs cover ratio).
- A sub-unit underpayment is accepted; `tecINSUFFICIENT_PAYMENT` needs a real shortfall — reflect
  that in the copy.

## Friction to capture
- Which codes were most misleading before the explanation (generic `tec*`)?
- Did seeing the cause + fix inline reduce confusion versus the raw code?
