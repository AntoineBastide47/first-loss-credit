# Part 6.0 — UI Foundation (shared infrastructure, not a phase)

Part 6 (UI) · Project: first-loss-credit · Target app: `apps/web` (the scaffold).

## What Part 6 is
A browser UI for the first-loss institutional-credit flow. It is **independent of the backend
parts (1-5)** and **parallelizable with them**: the UI reads and writes the live hackathon
devnet through the shapes already verified in Part 1, so it can be built now, while the next
backend part is in progress. Backend parts add protocol features; the UI surfaces whatever is
live and mocks the rest behind a flag.

## Independence model for Part 6
- `6.0` (this file) is **shared UI infrastructure**, the UI analogue of `lib/`. It is **not a
  phase**. Every UI phase composes it.
- Each UI phase (`6.1`-`6.5`) is an **independent screen**: it references no other UI phase and
  no backend phase, depends on no future phase, and reads no other phase's runtime state. It
  takes the ledger ids it needs as **inputs** (a scenario config or a paste field), never from
  another phase.
- UI phases may share code (this foundation + `lib/`); they must not depend on one another.

## Tech baseline (reuse the scaffold)
- `apps/web`: Next.js (App Router) + React + Tailwind + the existing component kit
  (`class-variance-authority`, `lucide-react`). Keep it; do not add a second framework.
- **Bump `xrpl` to `5.2.0-beta.1`** (matches `impl/`; needed for in-browser LoanSet counterparty
  signing — `signLoanSetByCounterparty` uses the `CPT` prefix this devnet requires).
- `xrpl-connect@^0.8.2` for wallet connect/sign. Browser polyfills (`buffer`,
  `crypto-browserify`, `stream-browserify`) are already in `apps/web`.

## Shared browser modules this foundation provides
- `lib/xrpl-client.js` — a single shared `Client` (connect once, reuse), reconnect handling.
- `lib/lending-read.js` — **read-only** helpers mirroring `impl/lib`: `readVault(vaultId)`,
  `readBroker(id)`, `readLoan(id)`, `shareBalance(acct, shareMptId)`, and derived getters:
  `sharePrice = AssetsTotal / OutstandingShares`, `utilisation =
  (AssetsTotal - AssetsAvailable) / AssetsTotal`, `coverRatio = CoverAvailable /
  (DebtTotal * CoverRateMinimum/100000)`. No value is stored on-ledger; all are derived here.
- `lib/format.js` — drops↔XRP, high-precision decimal display (loan fields are base-unit strings
  with a fraction; never parse to JS number for money — format from strings/BigInt).
- `lib/scenario.js` — an optional **demo seeder** (dev-only) that builds a vault/broker/loan via
  the same protocol shapes so a screen has something to show; guarded behind a `?demo` flag. It
  is infrastructure, not a phase, and screens never import another phase to get ids.
- `ui/` — shared presentational components (StatCard, AmountInput, TxButton that signs via
  xrpl-connect and links to the explorer, CodeBadge for `tec*` results, theme).

## Wallet / signing strategy (stated once)
- User-initiated single-signer txs (`VaultDeposit`, `VaultWithdraw`, `LoanBrokerCoverDeposit`,
  `LoanBrokerCoverWithdraw`, `LoanPay`, `LoanManage`) sign through the connected wallet.
- `LoanSet` needs **two** signatures. The loan desk (`6.3`) defines the in-browser flow
  (borrower signs, counterparty adds `CounterpartySignature` via `signLoanSetByCounterparty`);
  for a single-operator demo both keys may be loaded, with a two-party handoff as the real path.

## Cross-cutting UI rules
- **Derive, never assume stored.** Share price, utilisation, yield, cover ratio are computed from
  `vault_info` / broker reads, not read from a field.
- **Money is base-unit.** Format from strings/BigInt; round a payable amount **up** to the whole
  base unit (reuse the verified rule).
- **Every write shows its result code and an explorer link**, including `tec*` rejections, with a
  plain-language cause (see `6.5`).
- **Read-after-write:** refresh the affected ledger object on a validated ledger before updating
  the view.
- Responsive to phone width; theme-aware; no secret (faucet `secret`, seeds) is ever logged or
  sent anywhere but the signing path.
