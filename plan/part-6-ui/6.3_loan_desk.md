# Phase 6.3 — Loan Desk

Part 6 (UI) · Spec surface: XLS-66 (LoanSet dual-signature, LoanPay) · Composes `6.0` + `lib/`.

## Objective
Originate a loan with the two-party `LoanSet` and run repayments from the browser: the richest
UI flow, showing the counterparty co-signature and the per-payment split.

## Independence contract
Inputs: a `LoanBrokerID` (scenario config or paste field) and the signing keys described below.
References no other UI phase and no backend phase; depends on no future phase; reads no other
phase's runtime state.

## Inputs this phase takes
- `LoanBrokerID`; the borrower wallet and the counterparty (broker owner) signer.

## The two-signature flow (the core UI problem)
`LoanSet` carries the borrower's `TxnSignature` **and** the owner's `CounterpartySignature`.
Two supported modes:
- **Single-operator demo:** both keys loaded locally. Borrower signs the autofilled `LoanSet`;
  `signLoanSetByCounterparty(ownerWallet, signedBlob)` (xrpl `5.2.0-beta.1`) adds the second
  signature; submit the combined blob.
- **Two-party handoff (real path):** borrower signs and exports the blob (copy/QR/share link);
  the owner imports it, counter-signs, and submits. Show both steps as a wizard.
Fee must cover both signers (the SDK autofill accounts for this).

## Views
| View | Purpose |
|------|---------|
| Originate | terms form (principal, InterestRate, PaymentInterval, PaymentTotal, GracePeriod, fees) + signature wizard |
| Loan card | `PrincipalOutstanding`, `TotalValueOutstanding`, `PaymentRemaining`, `NextPaymentDueDate`, `PeriodicPayment` |
| Repay | pay the periodic amount; early full settlement with `tfLoanFullPayment` when `PaymentRemaining > 1` |

## Components and data flow
- Originate: build `LoanSet { LoanBrokerID, PrincipalRequested: <string>, Counterparty: owner,
  ...terms }`; run the two-signature flow; on success read the new `Loan` (id from metadata).
  Show borrower receipt = `Principal − LoanOriginationFee` and that `AssetsTotal` is **unchanged**
  at origination (cash basis).
- Repay: `LoanPay { LoanID, Amount }` where `Amount = roundUp(PeriodicPayment)`; disable/guard the
  cases the protocol rejects (see below). Offer the early-full-payment flag only when
  `PaymentRemaining > 1`.

## Build steps
1. Route `/loan`; originate wizard (terms → borrower sign → counterparty sign → submit).
2. Loan card from `readLoan(LoanID)`, refreshed after each write.
3. Repay control computing `roundUp(PeriodicPayment)`; show principal/interest split from the
   before/after loan read and the vault's `AssetsAvailable` rise.

## Acceptance checks
- A valid two-signed `LoanSet` succeeds; a blob missing the counterparty signature is rejected
  (surface the result). Borrower balance rises by `Principal − fee`; owner receives the fee.
- On-time `LoanPay` of the rounded-up periodic succeeds; `PaymentRemaining` decrements.
- Guarded negatives shown with their codes: final-payment `tfLoanFullPayment` → `tecKILLED`;
  underpayment → `tecINSUFFICIENT_PAYMENT`; late without the late flag → `tecEXPIRED`.

## Verification
Explorer links for `LoanSet` (both signatures visible) and each `LoanPay`.

## Precision / UX rules
- `PrincipalRequested` is a string; `LoanPay.Amount` is a base-unit string for XRP (or an MPT
  object in an MPT vault). Round the payable amount **up**.
- Never expose or persist the counterparty's key beyond the signing step.

## Friction to capture
- How hard was the two-party signature to model in a browser wizard?
- Did cash-basis interest (no `AssetsTotal` change at origination) surprise the operator?
