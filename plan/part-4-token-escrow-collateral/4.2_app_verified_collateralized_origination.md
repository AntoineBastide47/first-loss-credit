# Phase 4.2 — Application-Verified Collateralized Origination

Part 4 (Loaded: TokenEscrow collateral) · Spec: XLS-85 + XLS-66.

## Objective
Originate a loan backed by token collateral that the borrower locks in escrow. The link is
**application-enforced**: the protocol does not check the escrow, so the application verifies
it before submitting `LoanSet`.

## Scope correction (important)
- `LoanSet` does **not** verify an escrow. There is no protocol binding between a loan and an
  escrow. The application must read the **validated** escrow and check its owner, destination,
  asset, amount, and release conditions **before** it submits `LoanSet`.
- There is **no persistent ledger link** in either direction. `LoanSet.Data` is a transaction
  blob; the `Loan` object's persistence of it is unconfirmed, so do **not** rely on reading it
  back from the object. Keep the escrow↔loan mapping in **application state**, recover it from
  `LoanSet.Data` in **transaction history**, or use transaction **memos**.

## Independence contract
Inputs: none. Outputs consumed downstream: none. This phase issues its own token, funds a
vault, creates a broker with cover, locks collateral in escrow, then originates the loan.

## Preconditions this phase builds
1. Fund `issuer`, `lender`, `owner` (vault + broker owner), `borrower`.
2. Escrow-eligible token minted to `borrower`.
3. Vault (XRP or MPT) funded by the lender; broker with cover and debt capacity.

## Transaction steps (exact fields)
1. **EscrowCreate**, `Account=borrower`.
   - `Amount`: the collateral token amount.
   - `Destination`: `owner` (the broker owner). Do **not** use the broker pseudo-account —
     protocol rules govern its assets and `CoverAvailable` would not increase.
   - `FinishAfter`/`Condition`/`CancelAfter` matching the loan term.
   - Record the escrow's `Owner` + `OfferSequence` (its create `Sequence`).
2. **Application verification (off-ledger, mandatory):** fetch the validated escrow object;
   assert `Owner == borrower`, `Destination == owner`, token issuer/asset and `Amount` meet
   the collateral requirement, and the finish/cancel timing matches the loan. Abort if any
   check fails. Do not skip this; it is the whole point of this phase.
3. **LoanSet** (`tt=80`), dual-signed (reproduce the 1.3 procedure).
   - Optionally set `LoanSet.Data` to the escrow reference for the transaction record, but
     **persist the escrow↔loan mapping in application state** (and/or a transaction memo),
     since the `Loan` object may not expose `Data`.

## Expected results and assertions
- Step 2 gate: a mismatched escrow (wrong amount/destination/timing) must stop origination in
  the application; assert the abort path.
- `LoanSet` `tesSUCCESS`; standard origination state changes (reproduce 1.3's assertions).
- Confirm the ledger imposes **no** escrow→loan constraint (read both objects; they are
  independent on-chain).

## Explorer verification
Record the collateral `EscrowCreate` and the `LoanSet`; show the mapping recorded in your
application state / memo (not read back from the `Loan` object).

## Precision and timing rules
- Set the escrow `CancelAfter` beyond the loan's final due date so collateral cannot be
  reclaimed mid-loan by the borrower.
- `LoanSet.Data` is a hex blob (≤256 B); it is not a reliable persistent link — treat it as a
  transaction-history breadcrumb, not object state.
