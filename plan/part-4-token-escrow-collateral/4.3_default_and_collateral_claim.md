# Phase 4.3 — Default and Collateral Claim

Part 4 (Loaded: TokenEscrow collateral) · Spec: XLS-85 + XLS-66.

## Objective
Default a collateralized loan and claim the token collateral from escrow, proving that
default and recovery are **two separate, non-atomic transactions** and that the escrow
release is independent of loan status.

## Scope corrections (important)
- `LoanManage` default does **not** release the escrow. Recovery is a separate `EscrowFinish`.
- Escrow release **cannot be gated on default**. Once `FinishAfter` passes, settlement is
  independent of loan status. To give the broker real control, use a crypto-`Condition` whose
  `Fulfillment` the broker reveals **only** on default, rather than a time-only escrow — even
  then this is application-enforced, not protocol-enforced.
- `EscrowFinish` can still fail independently on timing, authorization, freeze, or lock. Plan
  for both transactions and a failed-finish path.

## Independence contract
Inputs: none. Outputs consumed downstream: none. This phase builds its own token, escrow,
vault, broker (with cover), and loan, then lets the loan default.

## Preconditions this phase builds
1. Fund `issuer`, `lender`, `owner` (vault + broker owner), `borrower`.
2. Collateral token minted to `borrower`; escrow locked with `Destination=owner` and a
   crypto-`Condition` (preferred) or a `FinishAfter` reachable around the default window.
3. Vault funded; broker with cover; one loan (short interval/grace). Keep the escrow↔loan
   mapping in application state / tx history (the `Loan` object may not expose `Data`).

## Transaction steps (exact fields)
1. Let the loan go overdue, then advance one validated ledger **strictly beyond**
   `NextPaymentDueDate + GracePeriod` (shared `lib/` timing helper `waitUntilAfter`).
2. **LoanManage default** (`tt=82`), `Account=owner`, `LoanID`,
   `Flags=tfLoanDefault` (`0x00010000`). First-loss cover is liquidated to the vault;
   residual is a vault loss (same first-loss recovery invariants as the default-recovery flow).
3. **EscrowFinish**, `Account` (any submitter; `owner` here), `Owner=borrower`,
   `OfferSequence` (the escrow create's sequence), plus `Condition` + `Fulfillment` if a
   crypto-condition was used. Collateral moves to `owner`.

## Expected results and assertions
- Step 2: `lsfLoanDefault` set; `CoverAvailable` drops by `DefaultCovered`; vault loss =
  `DefaultAmount - DefaultCovered` (see 1.4 for the full vault state change).
- Step 3: `EscrowFinish` `tesSUCCESS` → collateral delivered to `owner`.
- **Non-atomicity proof:** between step 2 and step 3 the loan is defaulted but the collateral
  is still escrowed. Read both states and show the gap.
- **Independence proof / failed-finish control:** attempt `EscrowFinish` before `FinishAfter`
  or without the `Fulfillment` (or with a frozen token) → the relevant `tec` code; record the
  exact value. This shows recovery is not guaranteed by, or tied to, default.

## Explorer verification
Record `LoanManage` default and `EscrowFinish` (success and the failed control) hashes.

## Precision and timing rules
- Default timing as in 1.4 (strictly beyond grace). A `Condition`-based escrow lets the broker
  choose when to release; a time-only escrow releases regardless of loan status once
  `FinishAfter` passes.
- Compare high-precision loss figures with an asset-unit tolerance.

## Friction to capture
- How much coordination did default-then-recover need given no atomic release?
- Could you actually gate release on default, or only approximate it with a crypto-condition?

## xrpl.js references
`LoanManage` (default flag), `EscrowFinish` (`Owner` + `OfferSequence`) models; ledger reads
for loan and escrow.

## XLS references
XLS-66 §3.10 (default, cover liquidation); XLS-85 TokenEscrow (finish conditions and failure
modes; no coupling to loan state).
