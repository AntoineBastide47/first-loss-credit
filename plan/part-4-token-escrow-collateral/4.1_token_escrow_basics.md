# Phase 4.1 — Token Escrow Basics

Part 4 (Loaded: TokenEscrow collateral) · Spec: XLS-85 TokenEscrow.

## Objective
Lock a token (IOU or MPT) in an escrow and release it, learning the TokenEscrow mechanics
and constraints that the collateral flow depends on.

## Independence contract
Inputs: none. Outputs consumed downstream: none. This phase issues its own token and builds
one escrow it finishes and one it cancels.

## Key constraints (design)
- **`EscrowCreate` has no `Data` field** (fields: `Amount`, `Destination`, `DestinationTag`,
  `CancelAfter`, `FinishAfter`, `Condition`). You cannot store a back-reference to a loan on
  the escrow. Correlation to a loan is one-way (store the escrow id in application state /
  `LoanSet.Data` on the transaction, Part 4.2) or via a shared memo on the `EscrowCreate`
  **transaction**.
- **Locking permission:**
  - **IOU:** the *issuer* sets the account flag `asfAllowTrustLineLocking` via `AccountSet`
    (an **account** flag, **not** a trust-line flag).
  - **MPT:** an escrow between non-issuer accounts needs **both** `tfMPTCanEscrow`
    (`0x08`) and `tfMPTCanTransfer` (`0x20`) on the issuance.
- **`EscrowFinish`** uses `Owner` + `OfferSequence` (the create's sequence). xrpl@5.1.0 has
  **no** ledger-ID-only form. **Any** account may submit it; a crypto-`Condition`, not the
  submitter, controls release.

## Preconditions this phase builds
1. Fund `issuer`, `owner` (escrow creator), `destination`.
2. Issue an escrow-eligible token (IOU with `asfAllowTrustLineLocking`, or MPT with
   `tfMPTCanEscrow` + `tfMPTCanTransfer`); give `owner` a balance.

## Transaction steps (exact fields)
1. **EscrowCreate**, `Account=owner`.
   - `Amount`: the token amount (IOU `{currency,issuer,value}` or MPT `{mpt_issuance_id,value}`).
   - `Destination`: `destination`.
   - Release condition: `FinishAfter` (time) and/or `Condition` (crypto-condition);
     `CancelAfter` for expiry.
   - Note the create's `Sequence` (needed as `OfferSequence` for finish/cancel).
2. **EscrowFinish**, `Account` (any submitter), `Owner=owner`, `OfferSequence` (the create's
   sequence), plus `Condition` + `Fulfillment` if a crypto-condition was set. Expect the
   token to move to `destination`.
3. On a second escrow: **EscrowCancel** after `CancelAfter`, `Owner=owner`, `OfferSequence`,
   returning the token to `owner`.

## Expected results and assertions
- `EscrowCreate` `tesSUCCESS`; escrow object holds the token; owner's spendable balance drops.
- `EscrowFinish` after `FinishAfter` (with a valid `Fulfillment` if conditioned) → token
  delivered to `destination`.
- `EscrowFinish` before `FinishAfter`, or a wrong `Fulfillment` → the relevant `tec`/`tem`
  code (record the exact value; do not assume).
- `EscrowCancel` after `CancelAfter` → token returned to `owner`.

## Explorer verification
Record `EscrowCreate`, `EscrowFinish`, and `EscrowCancel` hashes; show token custody moves.

## Precision and timing rules
- `FinishAfter`/`CancelAfter` use XRPL ripple-time seconds; advance validated ledgers to
  cross them.
- MPT/IOU amounts follow their own unit rules; no rounding subtlety beyond the token unit.

## Friction to capture
- Was the no-`Data`-field limitation clear before you tried to link the escrow to a loan?
- Was the IOU account-flag vs MPT issuance-flag split for locking discoverable?

## xrpl.js references
`EscrowCreate` (no `Data`), `EscrowFinish` (`Owner` + `OfferSequence`), `EscrowCancel`,
`AccountSet` (`asfAllowTrustLineLocking`) models; token `Amount` typing.

## XLS references
XLS-85 TokenEscrow (token-enabled escrow, locking flags, finish/cancel conditions).
